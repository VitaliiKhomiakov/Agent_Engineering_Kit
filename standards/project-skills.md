# Consumer-project task skills

Read when selecting an adopted AEK task skill or resolving its local inputs and
result boundary. Skills add task entries to existing standards; they do not
replace project instructions or become new technical-policy owners. Availability
comes from the optional `project-workflows` profile under the
[catalog contract](catalog.md). Installation, update and recovery remain owned by
the identified source's MIGRATION procedure, not by this task-time guide.

The table links inactive bundle templates for reference. Use the selected native
skill paths recorded in the active project entry when installed. Reading a template
directly is a fallback, not proof of native discovery. Select the entry for the
current operation; these are not a mandatory design → implementation → review
chain. Direct rules remain available without any skill. A completion review uses
the existing review boundary, not an extra cycle because a review entry exists.

## Resolve local inputs

Start from the affected project's active instructions, architecture/passport and
canonical task. Reuse supplied context that still matches the project. Establish
the current owners and interfaces from the affected files; distinguish observed
behavior from proposed design and accepted exceptions from incidental legacy code.

Use the local entry/passport's selected profile paths and actual stack. Follow
their task tables to relevant topics/sections. A catalog dependency supplies files;
it does not require reading them. A language does not establish its web framework,
database, host or optional libraries. Read examples only to resolve a specific
decision. Do not scan all standards or consult adoption provenance for ordinary
task work. The original AEK checkout is not an operational dependency.

If a needed profile or local route is absent, identify the exact missing guidance
and the decision it affects. Continue supported work through existing local rules;
do not install a profile, infer its policy, or call model/integration setup. A
material unresolved decision follows the existing [task contract](delivery-workflow.md#minimal-task-contract).

## Compose one procedure

Use the [core task routes](core.md#read-by-task) for engineering decisions and
[verification](verification.md) for evidence selection. Their rule ownership,
conditions and required project gates remain intact when no skill activates.

When a Superpowers procedure applies, first use the
[local adaptations](superpowers.md); reuse a procedure already satisfied for this
task. The AEK entry contributes technical-reference selection and the result
contract below, not another brainstorming, planning, review or Git workflow.
When the plugin is unavailable, use the existing direct scoped-task fallback.
Read the guide as reference without re-invoking its listed entry. Neither the
guide nor a template changes native instruction precedence.

## Design result

Record the result in the existing canonical task/design location according to
the adopted planning policy. A bounded decision may remain in the response when
that policy permits it. Do not create a parallel plan or move a native task store.
Include the parts needed for the affected behavior:

- Outcome, scope, compatibility and material open decisions.
- Current and proposed owners at actual project paths, changed interfaces and
  permitted dependencies; resource, state or transaction lifetime where relevant.
- Selected technical rules with the design decision each informs. Explain a
  meaningful alternative or tradeoff when it changes the chosen design.
- Observable acceptance cases and sufficient existing or proposed checks,
  distinguishing a planned check from executed evidence.

Preserve the project's integration model: backend layers are not a default for
UI, gameplay or editor work. Keep details proportional to the change; an output
contract is not a quota of sections, patterns, tests or new files. Implementation
starts under the existing design/progression decision, not automatically because
the skill produced a design.

## Implementation result

Use the existing canonical task/result to connect the changed behavior and actual
paths to its accepted design and applicable stack rules. Report the evidence for
its acceptance criteria, the remaining material findings or unavailable gates,
and the next checkpoint under the selected work mode. Distinguish checks actually
executed from planned checks and still-valid evidence reused for unchanged inputs.

This is an output boundary, not another delivery procedure. Baseline preservation,
test selection/cadence, review, completion and progression remain with
[delivery](delivery-workflow.md), [verification](verification.md) and
[work modes](work-modes.md). A small fix does not require a new design document.

## Review result

Use [review boundaries](verification.md#review-boundaries) to determine scope,
independence and finding disposition. Connect findings to actual project paths
and the affected contract: consequence, concrete failure scenario, supporting
evidence and the uncertainty that remains. Rank material findings by consequence;
keep optional improvements and incidental pre-existing issues distinct.

Include the baseline/scope reviewed, evidence used and important coverage limits.
If no findings remain, say so for that scope without certifying unexamined code.
Self-review is not independent review. Put the result in the requested review
surface or existing task; do not create another plan or editable progress ledger.
Review-only authorization does not extend to fixing the findings.
